# 07. Аудит информационной безопасности и защиты персональных данных

Версия 0.1 · 31.10.2026. Сделан по архитектуре, макетам и разбору витрины Kartop. Это проектный аудит: кода ещё нет, поэтому каждый пункт ниже — требование к разработке и проверке перед запуском.

## 1. Какие данные мы храним и кто их видит

| Данные | Чьи | Кто видит | Риск утечки |
|---|---|---|---|
| Телефон, имя | Покупатель | Магазин — только после принятия заказа; курьер — только во время доставки; саппорт — маскировано | Высокий: спам, мошенничество, «увод» клиентов |
| Точный адрес, подъезд, квартира, домофон, комментарий | Покупатель | То же, что телефон | Очень высокий: физическая безопасность, кражи |
| История заказов | Покупатель | Покупатель; магазин — только свои заказы | Средний: профилирование |
| Телефон, Kaspi-номер, ИИН/БИН, адрес | Магазин | Админы платформы; Kaspi-номер — покупателю только после принятия заказа | Средний: Kaspi-номер часто личный номер продавца |
| Геопозиция устройства | Покупатель, курьер | Только для подбора адреса и доставки | Средний |
| Фото товаров | Магазин | Публично | EXIF может содержать координаты дома продавца |

## 2. Главные риски и меры

### 2.1 Магазин получает данные клиента
- **До принятия** API отдаёт только район, расстояние (округлённо до 0,1 км), окно, состав и сумму. Маскировка делается на сервере в DTO по статусу заказа, не в приложении.
- **После завершения** заказа через 7 дней адрес и телефон у магазина снова скрываются. В истории остаются только район и сумма.
- Нет экспорта клиентской базы для магазина. Повторные заказы идут через платформу.
- Каждый просмотр полного адреса и телефона пишется в аудит-лог: кто, когда, какой заказ.
- v1: звонок через подменный номер (call masking), магазин не видит реальный номер.

### 2.2 Перебор чужих заказов (IDOR)
- ID заказов — UUID, а не порядковые номера. «№ 20481» — только отображаемый номер, по нему доступа нет.
- Ссылка на отслеживание заказа содержит подписанный токен с ограниченным сроком.
- «Мои заказы» без регистрации привязаны к токену устройства, а не к поиску по телефону.
- Изоляция магазинов: Row-Level Security в Postgres по `store_id` плюс проверка в каждом запросе. Автотесты «магазин A не видит заказы магазина B».

### 2.3 Подделка и злоупотребление OTP
- Это и защита денег («SMS pumping» — накрутка платных SMS ботами), и защита от фейковых заказов. Подробно — в `08-otp-and-launch.md`.
- Лимиты: не больше 3 кодов на номер за 15 минут и 10 в сутки, лимиты на IP и устройство. Код из 6 цифр, живёт 5 минут, 5 попыток. В базе хранится только хэш.
- Отправка только на казахстанские номера (+7 7xx). Международные префиксы отклоняются.
- Невидимая капча Cloudflare Turnstile на вебе перед отправкой кода.
- Сравнение кода в постоянное время, одинаковый ответ «код отправлен» для любых номеров — чтобы нельзя было проверить, зарегистрирован ли номер.

### 2.4 Фейковые заказы и вред магазину
- SMS-код на первый заказ с номера; далее — доверенное устройство.
- Магазин может заблокировать номер. После 2 неполученных заказов номер автоматически уходит на подтверждение звонком.

### 2.5 Админка — самая ценная цель
- Вход только через SSO + второй фактор (passkey или TOTP). Без паролей в чате и общих аккаунтов.
- Доступ по VPN или по списку IP.
- Роли с минимальными правами. ПДн по умолчанию маскированы, «Показать» — с указанием причины и записью в аудит-лог.
- Вход «от имени магазина» (impersonation) только для саппорта, с логом и уведомлением магазину.

### 2.6 Приложение магазина на общем телефоне
- Часто один телефон на прилавке у нескольких продавцов. Блокировка приложения PIN-кодом или биометрией, автоматический выход через N часов бездействия.
- Список устройств и удалённый выход в приложении владельца.
- Роли: продавец не видит выручку и настройки, курьер видит только свои доставки.

### 2.7 Kaspi-номер продавца
- У Kartop номер Kaspi продавца виден любому посетителю ещё до заказа. Это утечка личного номера.
- У нас номер показывается покупателю только после принятия заказа и только на странице этого заказа.

### 2.8 Логи, аналитика, ошибки
- В логах нет телефонов, адресов и кодов. Маскирование на уровне логгера, проверка в CI.
- В Sentry и аналитике — только псевдонимные ID. Включена очистка полей (scrubbing).
- Логи хранятся 30 дней, аудит-лог — 1 год.

### 2.9 Файлы и фото
- Загрузка через presigned URL с проверкой типа и размера. Перекодирование через imgproxy удаляет EXIF, в том числе GPS.
- Публичны только фото каталога. Фото собранного заказа (v1) — по подписанной ссылке с коротким сроком.

### 2.10 Веб
- Cookies HttpOnly + Secure + SameSite, защита от CSRF, строгий CSP, HSTS.
- Публичный API каталога с лимитами и кешем: нельзя массово выкачать данные магазинов.
- Никаких списков клиентов и заказов в публичном API (у Kartop публичны только каталог и статус магазина — так и надо).

### 2.11 Инфраструктура
- Секреты — в Secret Manager, не в коде и не в переменных CI.
- База недоступна из интернета, доступ через bastion с MFA. Шифрование дисков и бэкапов, ежемесячная проверка восстановления.
- Зависимости — Renovate + сканирование уязвимостей в CI. Образы контейнеров — сканирование перед деплоем.

## 3. Закон РК о персональных данных (требует проверки юристом)
- Основной акт — Закон № 94-V «О персональных данных и их защите» с поправками 2026 года (закон № 326-VIII, в силе с 25.08.2026). Пункт 2 статьи 12 требует хранить ПДн граждан РК в базах на территории Казахстана.
- **Вывод для архитектуры:** основная база с ПДн, бэкапы и файлы с ПДн — только в дата-центре в Казахстане. За рубежом могут быть только обезличенные данные (CDN фото каталога, обезличенная аналитика).
- Статья 10-1 (новая) — уведомление уполномоченного органа о начале обработки ПДн. Сделать до запуска.
- Нужны: политика конфиденциальности, согласие на обработку ПДн при первом заказе (галочка + ссылка), процедура удаления данных по запросу, порядок уведомления об утечке.
- Отправка телефона в Telegram или WhatsApp для OTP — это передача ПДн третьему лицу. Указать в политике и согласии.
