# 24. Правило: спаривание email ↔ телефон только после подтверждения обоих

**Зафиксировано.** Email и телефон связываются (спариваются) ТОЛЬКО когда доказано
владение обоими:
- **телефон** — подтверждён OTP (код на телефонный канал: Telegram/WhatsApp/SMS);
- **email** — подтверждён отдельным кодом, отправленным НА ЭТОТ email.

Привязка происходит только после подтверждения email. Без этого — никак. Непроверенный
email в `User.email` не попадает (ни из формы заказа, ни из параметра запроса кода).

> Это исправляет прежнее поведение (docs/21, docs/22), где email привязывался без
> подтверждения. Теперь привязка — только через `auth/email/*`.

## 24.1 API

Шаг эл. почты требует access-токен (телефон уже подтверждён → userId из сессии):

```
POST /auth/email/request { email }   # код на этот email; email, занятый другим → 400
POST /auth/email/verify  { code }     # верный код → email привязывается к аккаунту
```

Правила: некорректный email → 400; email занят другим аккаунтом → 400; неверный код →
400 (без привязки); лимит запросов как у OTP. После привязки запрос OTP по телефону
отправляет код на **подтверждённый** email (дешевле SMS, docs/20 §5).

Проверено e2e: без токена → 401; занятый email → 400; неверный код → не спарено;
верный код → спарено; далее OTP по телефону уходит на email.

## 24.2 B2C-флоу: сначала телефон, затем обязательный email

Покупатель заходит по телефону (подтверждён OTP) и может пользоваться. Но мы
**мотивируем/обязываем** добавить и подтвердить email, чтобы потом слать коды и
уведомления на почту (снижение косто-OTP).

Логика «вынужденного» email (для приложения покупателя):
1. Первый заказ/вход — только телефон (OTP). Email ещё нет.
2. Сразу после первого заказа — экран «Добавьте email, чтобы следить за заказами и
   получать коды быстрее»: ввод email → код на почту → подтверждение → привязка.
3. **Мягкий барьер:** на следующем входе/перед вторым заказом шаг добавления email —
   обязательный (пропустить нельзя, кроме «позже» ограниченное число раз).
   Трекинг заказа и история доступны полноценно только после привязки email.
4. Повторная верификация с доверенного устройства не требуется (trustedUntil).

Так телефон остаётся основным идентификатором (нужен для доставки/связи), а email
становится основным каналом доставки кодов/уведомлений — почти бесплатным.

Эндпоинты для этого уже есть (`auth/email/*`); экран — в приложении покупателя
(когда появится нативный клиент) и/или в приложении магазина (для сотрудников).
